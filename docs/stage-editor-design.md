# ステージエディタ & ステージJSON自動取り込み 設計書

- 対象リポジトリ: `jphacks2026_s.suex`（ショートカット・ダンジョン）
- ステータス: ドラフト v1
- 作成日: 2026-10-21
- 目的: ノンエンジニアでもステージを作成でき、保存したJSONを置くだけでCloudflareのビルドにステージが反映される仕組みを設計する

---

## 1. 目的とゴール

### 1.1 解決したい課題

現在ステージは `src/data/stages.js` にJavaScriptオブジェクトとして直接記述されている。ステージを追加するにはコードを編集する必要があり、次の問題がある。

- どこに何を置くかがコードを読まないと分からない
- 座標の手計算が必要でミスしやすい
- 追加のたびにゲーム側のコード変更・レビューが必要
- ステージ制作者とゲーム開発者の分業がしづらい

### 1.2 ゴール

1. **ブラウザで動くステージエディタ**を別サイトとして提供する
2. グリッド上に壁・開始位置・ゴール・アイテム・木箱などを配置し、見た目でステージを作れる
3. ステージを**JSON形式で書き出す**（または公開API経由でリポジトリに追加する）
4. リポジトリの所定フォルダにJSONを置いてビルドするだけで、**コード変更なしにステージが追加・並び替えされる**
5. 不正なステージはエディタとビルドの両方で検出し、壊れたステージが本番に出ないようにする
6. 既存2ステージをJSONへ移行しても、現在のゲームプレイが維持される

### 1.3 非ゴール（今回のスコープ外）

- ステージ内のボス・クイズ定義（現状はゲーム全体で固定。将来拡張として予約）
- ステージのオンライン同時編集
- スマートフォンでの快適な編集（閲覧・簡易編集のみ考慮）
- ステージのサーバー側データベース保存（JSONを正とする）
- ゲーム本体の課金・認証・ランキング

### 1.4 完了条件（要約）

- `src/data/stages/*.json` を追加してmainブランチへpushすると、Cloudflareのゲームサイトが自動ビルドされ、番号順にステージが追加される
- エディタで既存JSONを読み込み、編集し、再出力できる（往復で意味が変わらない）
- 不正なステージはエクスポート時とCIビルド時に拒否される
- エディタはゲームとは別URLで公開され、ゲーム本体のバンドルには含まれない

## 2. 現状の前提

### 2.1 ゲーム側の技術的前提

- 素のHTML + ES Modules + Canvas 2D。ビルドツール未導入（`package.json` なし）
- キャンバスは `960 × 640`、タイル `40px` → **24列 × 16行**
- 外周1タイルは固定の壁。実際に配置できるのは **x: 1〜22 / y: 1〜14**（22列 × 14行）
- 移動は1マス単位。プレイヤーの向いている方向の1マスが操作対象
- ステージデータは `STAGES` 配列で、`StageManager` が配列順に進行
- 既存ステージのフィールド:
  - `number`, `name`, `start {x,y,facing}`, `obstacles[]`, `items[]`, `blocks[]`, `goal {x,y}`
  - 任意: `goalBlock {x,y}`, `shortcutGate {x,y}`, `hint`
- `obstacles` は `{x, y, width, height}` の矩形
- ボス戦は**全ステージクリア後**に固定で1回
- アイテムは `skillPotion` と `lifePotion` の2種
- 木箱は `{id, name, kind, x, y, color}`。`kind` は `normal` / `colored`
- 色つき木箱と同じ色の `colorSwitches` にペーストすると、同色の `colorWalls` が開く

### 2.2 現状の制約からくる設計上の要点

- **JSONの座標系はタイル座標（0始まり、左上）**とし、ピクセル座標は保存しない
- 外周は編集不可。エディタ上でもロック表示する
- 既存の `number` を表示順・進行順の正とする
- アイテム・木箱・開始位置・ゴールなどは1マス1エンティティ
- 壁は矩形で保持しているが、エディタでは**タイル塗り**で編集し、出力時に矩形へ変換する（後述）
- ゲームはJSONを**ビルド時に静的import**する。実行時fetchにしない（404・CORS・読み込み順の複雑さを避ける）

## 3. 全体アーキテクチャ

### 3.1 構成概要

```
[ステージエディタサイト]                [ゲームサイト]
  editor.example.com                    game.example.com
  ・グリッド編集                        ・ステージJSONをビルド時に取り込み
  ・バリデーション                      ・番号順に自動進行
  ・JSONエクスポート / 公開API          ・Cloudflare Pagesで配信
          │                                      ▲
          │ 手動コミット または 公開API            │ main pushで自動ビルド
          ▼                                      │
  GitHub: src/data/stages/*.json ────────────────┘
          │
          └─ PR時にCloudflare Preview + CIバリデーション
```

### 3.2 2サイトを1リポジトリで管理する

- ゲームは現状のルート構成を維持する（破壊的移動を避ける）
- エディタは `editor/` サブディレクトリに独立したViteアプリとして置く
- Cloudflare Pagesの**プロジェクトを2つ**作り、同じリポジトリを参照する
  - ゲーム用: Root `/`、出力 `dist`
  - エディタ用: Root `editor`、出力 `editor/dist`
- 共通のステージ仕様（定数・バリデーション）は `packages/stage-schema/` に切り出し、両方から参照する

これにより、エディタのコードがゲームのバンドルに混入せず、デプロイも独立する。

### 3.3 公開フローは2段階で提供する

| フェーズ | 方式 | 対象 | 特徴 |
|---|---|---|---|
| A（MVP） | JSONをダウンロードし、GitHub Web UIまたはローカルで `src/data/stages/` に追加 | 全員 | 追加実装が少ない。Cloudflareはpushで自動ビルド |
| B（推奨） | エディタの「公開」ボタン → Cloudflare Pages Functions → GitHubへPR作成 | 制作チーム | ワンクリック公開。承認後にmainへマージで本番反映 |

**重要:** ホストされたWebサイトからローカルPCのフォルダへ直接ファイルを書き込むことはできない。そのため「エディタで保存したら即このフォルダに追加」を実現するには、BのGitHub連携が必要になる。Aだけでも「JSONを置いてビルドすれば追加」は満たせる。

## 5. ステージJSON仕様

### 5.1 ファイル命名規則

- 配置先: `src/data/stages/`
- ファイル名: `{id}.json`
  - 例: `crate-intro.json`, `copy-gate-maze.json`
- `id` は**作成後に変更しない**（将来のセーブデータ・クリア記録のキーになるため）
- 表示順・進行順はファイル名ではなく `number` で決める
- 1ファイル = 1ステージ。1ファイルあたり最大64KB

### 5.2 スキーマ（v1）

```json
{
  "schemaVersion": 1,
  "id": "crate-intro",
  "number": 1,
  "name": "切り取りと配置",
  "start": { "x": 2, "y": 7, "facing": "right" },
  "obstacles": [
    { "x": 8, "y": 1, "width": 1, "height": 6 },
    { "x": 8, "y": 8, "width": 1, "height": 7 }
  ],
  "items": [
    { "type": "skillPotion", "x": 3, "y": 5 },
    { "type": "lifePotion", "x": 6, "y": 12 }
  ],
  "blocks": [
    { "id": "stage-1-crate", "name": "木箱", "kind": "normal", "x": 3, "y": 7, "color": "#b57d50" }
  ],
  "colorSwitches": [
    { "x": 8, "y": 7, "color": "#ff5e68" }
  ],
  "colorWalls": [
    { "x": 12, "y": 4, "width": 1, "height": 7, "color": "#ff5e68" }
  ],
  "lasers": [
    { "x": 15, "y": 3, "direction": "down", "length": 6 }
  ],
  "magma": [
    { "x": 13, "y": 6 },
    { "x": 13, "y": 7 }
  ],
  "goal": { "x": 21, "y": 7 },
  "goalBlock": { "x": 18, "y": 7 },
  "shortcutGate": null,
  "hint": "木箱をCtrl+Xで切り取り、指定マスの前からCtrl+Vで配置"
}
```

### 5.3 フィールド定義

| フィールド | 型 | 必須 | 制約・意味 |
|---|---|---:|---|
| `schemaVersion` | number | ○ | 現行は `1`。将来の互換判定に使用 |
| `id` | string | ○ | `^[a-z0-9][a-z0-9-]{2,63}$`。全ステージで一意。ファイル名と一致 |
| `number` | integer | ○ | 1以上。全ステージで一意。進行順・表示順 |
| `name` | string | ○ | 1〜40文字。ステージ名 |
| `start.x`, `start.y` | integer | ○ | 配置可能範囲内。開始タイル |
| `start.facing` | string | ○ | `up` / `down` / `left` / `right` |
| `obstacles` | array | ○ | 固定壁の矩形。空配列可。各要素は後述 |
| `items` | array | ○ | 0件可。`type` は `skillPotion` / `lifePotion` |
| `blocks` | array | ○ | 0件可。操作可能な木箱。`kind` でノーマル / 色つきを指定 |
| `colorSwitches` | array | ○ | 0件可。色つき木箱を置くスイッチ。`{x, y, color}` |
| `colorWalls` | array | ○ | 0件可。同色スイッチが押されると開く壁。矩形で指定 |
| `lasers` | array | ○ | 0件可。一直線に伸びるビームの発射装置。`{x, y, direction, length}` |
| `magma` | array | ○ | 0件可。落下するとゲームオーバーになるマグマ。`{x, y}` |
| `goal` | object | ○ | ゴールタイル。`{x, y}` |
| `goalBlock` | object \| null | ○ | 箱を置く必要があるタイル。不要なら `null` |
| `shortcutGate` | object \| null | ○ | Ctrl+Cで開くゲート。不要なら `null` |
| `hint` | string | ○ | 0〜70文字。HUDに1行表示。空文字可 |

**配列は必ず出力する。** 任意フィールドを省略せず `null` または `[]` を明示することで、エディタ・ゲーム・検証の分岐を減らす。

#### obstacles 要素

| フィールド | 型 | 制約 |
|---|---|---|
| `x`, `y` | integer | 配置可能範囲内（外周不可） |
| `width`, `height` | integer | 1以上。`x + width - 1 <= 22`, `y + height - 1 <= 14` |

#### items 要素

| フィールド | 型 | 制約 |
|---|---|---|
| `type` | string | `skillPotion` または `lifePotion` |
| `x`, `y` | integer | 配置可能範囲内 |

#### blocks 要素

| フィールド | 型 | 制約 |
|---|---|---|
| `id` | string | ステージ内で一意。`^[a-z0-9][a-z0-9-]{0,31}$` |
| `name` | string | 1〜8文字。タイル内表示のため4文字以下を推奨 |
| `kind` | string | `normal`（ノーマル木箱）または `colored`（色つき木箱） |
| `x`, `y` | integer | 配置可能範囲内 |
| `color` | string | `^#[0-9a-fA-F]{6}$`。色つき木箱はスイッチと色を一致させる |

#### colorSwitches 要素

| フィールド | 型 | 制約 |
|---|---|---|
| `x`, `y` | integer | 配置可能範囲内 |
| `color` | string | `^#[0-9a-fA-F]{6}$`。対応する色つき木箱・カラー壁と同じ色 |

#### colorWalls 要素

| フィールド | 型 | 制約 |
|---|---|---|
| `x`, `y` | integer | 配置可能範囲内 |
| `width`, `height` | integer | 1以上。`x + width - 1 <= 22`, `y + height - 1 <= 14` |
| `color` | string | `^#[0-9a-fA-F]{6}$`。対応するスイッチ・色つき木箱と同じ色 |

色は大文字・小文字を区別しません。同じ色のスイッチが1つでも押されると、その色のカラー壁がすべて開きます。

#### lasers 要素

| フィールド | 型 | 制約 |
|---|---|---|
| `x`, `y` | integer | 配置可能範囲内。発射装置のタイル（通行不可） |
| `direction` | string | `up` / `down` / `left` / `right` |
| `length` | integer | 1〜21。発射装置の次のマスから数えたビームの長さ |

ビームは固定壁・閉じたゲート・閉じたカラー壁・別のレーザー発射装置で止まります。最初に当たったノーマル木箱に遮られ、その木箱タイルは安全になります。遮断した木箱は5秒で破壊され、ビームが再開します。色つき木箱はビームを遮りません。

#### magma 要素

| フィールド | 型 | 制約 |
|---|---|---|
| `x`, `y` | integer | 配置可能範囲内 |

マグマは床扱いで、木箱を配置できます。木箱がないマグマに入るとゲームオーバーです。ノーマル木箱を置いたマグマのマスだけ通行できます（色つき木箱は足場になりません）。

### 5.4 座標系と配置可能範囲

- 原点はキャンバス左上。`x` は右方向、`y` は下方向
- タイル `(x, y)` はピクセル `[x*40, (x+1)*40) × [y*40, (y+1)*40)`
- `x = 0`、`x = 23`、`y = 0`、`y = 15` は外周壁。**編集・配置不可**
- エディタはこの外周をロック表示する

### 5.5 エンティティの重なりルール

同じタイルに複数のものを置けない。以下はすべて相互に排他。

- 固定壁（obstacles）
- 開始位置
- ゴール
- `goalBlock`（箱を置く予定の空きマス）
- `shortcutGate`
- `colorSwitches`
- `colorWalls`
- `lasers`
- `magma`
- 初期配置の木箱
- アイテム

`goalBlock` と `shortcutGate` は「通過・配置の対象になる特殊な空きマス」であり、壁や別エンティティとは重ねられない。

### 5.6 バージョニング方針

- 破壊的変更時のみ `schemaVersion` を上げる
- 追加フィールドは原則として任意フィールドとして後方互換に追加し、`schemaVersion` は据え置く
- ゲーム側は未知の `schemaVersion` を**ビルドエラー**にする（黙って無視しない）
- 将来のボス定義は `boss` フィールドを任意追加する想定。現行v1では**未知フィールドを禁止**し、早期に誤記を検出する

## 6. ステージエディタ仕様

### 6.1 基本方針

- デスクトップブラウザ向け（推奨幅 1280px以上、最小 1024px）
- 外部UIフレームワークは任意。初期実装は素のJS + Canvasでよい（ゲームと同じ思想）
- 編集中データはメモリ上の1つのステージオブジェクトとし、描画は毎フレームではなく変更時のみ
- エディタのキャンバスは論理 `960 × 640`。表示はCSSで拡大縮小し、ポインタ座標は `getBoundingClientRect` からタイルへ変換する

### 6.2 画面レイアウト

```
┌──────────────────────────────────────────────────────────────┐
│ ヘッダー: ステージ名 / number / 保存状態 / 検証 / プレビュー / 出力 │
├──────────────┬──────────────────────────────┬────────────────┤
│ ツールパレット │        編集キャンバス          │ インスペクター   │
│ ・選択        │  24×16 グリッド               │ ・選択要素の属性 │
│ ・壁を塗る    │  外周ロック                   │ ・開始位置       │
│ ・壁を消す    │  ホバー座標表示               │ ・ゴール         │
│ ・開始位置    │  選択中エンティティの強調      │ ・goalBlock     │
│ ・ゴール      │                              │ ・shortcutGate  │
│ ・goalBlock  │                              │ ・木箱の名前/色  │
│ ・ゲート      │                              │ ・ヒント文       │
│ ・木箱        │                              │                │
│ ・青ポーション │                              │ ・検証結果一覧   │
│ ・赤ポーション │                              │                │
├──────────────┴──────────────────────────────┴────────────────┤
│ ステータス: タイル座標 / ズーム / 操作メッセージ / 自動保存表示   │
└──────────────────────────────────────────────────────────────┘
```

### 6.3 ツールと編集操作

| ツール | 操作 | 備考 |
|---|---|---|
| 選択 | クリックでエンティティ選択、ドラッグで移動 | ドラッグ中はゴースト表示 |
| 壁を塗る | クリック / ドラッグで壁タイルを追加 | 連続塗り対応。外周は無視 |
| 壁を消す | クリック / ドラッグで壁を削除 | 右クリックでも削除可 |
| 開始位置 | クリックで配置（1つのみ） | 既存の開始位置は移動 |
| ゴール | クリックで配置（1つのみ） | 既存のゴールは移動 |
| goalBlock | クリックで配置 / 再クリックで解除 | 0または1 |
| shortcutGate | クリックで配置 / 再クリックで解除 | 0または1 |
| 木箱 | クリックで配置 | 連続配置可。IDは自動採番 |
| 色つき木箱 | クリックで配置 | ギミック色を使用。連続配置可 |
| カラースイッチ | クリックで配置 | ギミック色を使用。同マス再クリックで色変更 |
| カラー壁 | クリック / ドラッグで配置 | ギミック色を使用。同色スイッチで開く |
| レーザー | クリックで配置 | 向き・長さをインスペクターで変更 |
| マグマ | クリック / ドラッグで配置 | ノーマル木箱を置くと渡れる |
| 青ポーション | クリックで配置（同マスに複数不可） | |
| 赤ポーション | クリックで配置（同マスに複数不可） | |

共通操作:

- `Ctrl/Cmd + Z` Undo、`Ctrl/Cmd + Y` / `Ctrl/Cmd + Shift + Z` Redo（最大100履歴）
- `Delete` / `Backspace` で選択要素を削除
- 矢印キーで選択要素を1マス移動（壁は塗り直し）
- `Esc` でツールを「選択」に戻す
- 右クリックは「消す」補助。ブラウザのコンテキストメニューはキャンバス上のみ抑止
- ブラウザ標準ショートカット（Ctrl+S等）は、エディタ内で意味を持つ場合のみ `preventDefault`

### 6.4 インスペクター

- ステージ属性: `id`（新規時のみ編集可、作成後は読み取り専用）、`number`、`name`、`hint`
- 選択要素の属性:
  - 木箱: `name`、`kind`（ノーマル / 色つき）、`color`（カラーピッカー + プリセット）、座標
  - カラースイッチ / カラー壁: `color`、座標
  - レーザー: `direction`、`length`、座標
  - マグマ: 座標
  - 開始位置: `facing`
  - アイテム: 種別、座標
  - 壁: 座標、幅、高さ（矩形単位で選択した場合）
- 未選択時はステージ属性と検証結果を表示

### 6.5 壁の表現と矩形変換

エディタ内部では壁を**タイルの集合**として保持する。JSON出力時に決定的なアルゴリズムで矩形へ変換する。

- 各行について、連続する壁タイルを水平方向に結合して1つの矩形にする
- 行ごとに独立して矩形化する（垂直結合は必須としない）
- 出力順は `y`、次に `x` の昇順で固定する
- インポート時は逆に矩形をタイルへ展開する

この方式により、制作者は直感的に塗るだけでよく、ゲーム側の既存 `obstacles` 形式とも互換を保てる。将来、垂直結合を加えてもゲームの挙動は変わらない。

### 6.6 バリデーション表示

- 編集のたびにローカル検証を実行し、右パネルにエラー / 警告を一覧表示
- エラーをクリックすると該当タイルへジャンプし、赤枠で強調
- エラーがある状態でも編集・下書き保存は可能。ただし**エクスポートと公開はブロック**する
- 警告のみの場合はエクスポート可能。確認ダイアログを出す

### 6.7 プレビュー

- 「プレビュー」でグリッド・カーソル・検証マーカーを消し、ゲームに近い見た目で表示
- 開始位置、ゴール、アイテム、壁、木箱、ゲートをゲームと同じ色・寸法で描画
- MVPでは静止プレビュー。操作プレビュー（実際に動かす）は将来拡張
- ゲーム側の描画関数を共有できるようになった段階で、プレビューを共通レンダラーへ差し替える

### 6.8 入出力

- **新規作成**: `id`、`number`、`name` を入力して開始
- **インポート**: ファイル選択またはドラッグ&ドロップ。検証に失敗した場合は読み込まず、エラー内容を表示
- **エクスポート**: `{id}.json` をUTF-8・2スペースインデント・末尾改行付きでダウンロード
  - File System Access API が使える環境では「名前を付けて保存」を優先し、非対応環境では通常ダウンロード
- **JSONをコピー**: GitHub Web UIでファイルを作成する際の貼り付け用
- **自動保存**: `localStorage` に下書きを500msデバウンスで保存。キーは `shortcut-dungeon:editor:draft`
  - 再訪時に復元確認
  - 下書きにはステージ本体と最終更新時刻のみ保存（個人情報なし）
- **既存ステージの読み込み**: エクスポート済みJSONをインポートして編集可能

### 6.9 エディタの対象外

- ボス・クイズの編集
- サウンド設定
- ステージの公開順ドラッグ並び替え（`number` 入力で代替。将来対応可）
- 複数人同時編集

## 7. バリデーション仕様

### 7.1 実行場所

1. エディタ内（即時）
2. エクスポート / 公開時（ブロック）
3. ローカルビルド前（`npm run validate:stages`）
4. GitHub Actions（PR時）
5. Cloudflareビルド（最終防衛線）

同じ検証ロジックを `packages/stage-schema/validate.js` に集約し、全箇所で使い回す。

### 7.2 エラー（ビルド・公開を失敗させる）

| ID | 内容 |
|---|---|
| E001 | JSONとして不正、または必須フィールド欠落 |
| E002 | `schemaVersion` が未対応 |
| E003 | `id` の形式不正 |
| E004 | `id` が他ステージと重複、またはファイル名と不一致 |
| E005 | `number` が1未満、または他ステージと重複 |
| E006 | `start` / `goal` が配置可能範囲外 |
| E007 | 壁が範囲外、`width` / `height` が0以下、またはレーザーの到達範囲が配置可能範囲外 |
| E008 | 同一タイルに複数エンティティが存在 |
| E009 | `goalBlock` / `shortcutGate` が壁・初期木箱・アイテム・ゴールと重複 |
| E010 | アイテム種別が未対応 |
| E011 | ブロックIDがステージ内で重複、または形式不正 |
| E012 | 色が `#rrggbb` 形式でない |
| E013 | `start` が壁・木箱・アイテム上にある |
| E014 | 未知フィールドが存在する |
| E015 | ファイルサイズが64KB超 |

### 7.3 警告（公開は可能）

| ID | 内容 |
|---|---|
| W001 | `goalBlock` があるのに、初期木箱が1つもない |
| W002 | `shortcutGate` があるのに、初期木箱が1つもない（コピー元が必要） |
| W003 | `number` が連番でない（欠番あり） |
| W004 | `name` が長い、`hint` が70文字超、木箱名が長い |
| W005 | 開始位置からゴールまで、壁と閉じたゲートだけを考慮した経路がない |
| W006 | アイテムが0個、またはポーション種別に偏りがある |
| W007 | 外周に接する壁がない（見た目の注意） |
| W009 | カラースイッチがあるのに色つき木箱がない |
| W010 | カラースイッチと同じ色の色つき木箱が初期配置にない |
| W011 | カラースイッチに対応するカラー壁がない |
| W012 | カラー壁に対応するカラースイッチがない |
| W013 | 色つき木箱に対応するカラースイッチがない |
| W014 | マグマがあるのに、足場用のノーマル木箱がない |
| W015 | レーザーがあるのに、遮るノーマル木箱がない |

### 7.4 到達可能性チェックの方針

- 経路探索は「開始位置 → ゴール」のBFS
- 壁、初期木箱、閉じている `shortcutGate`、レーザー発射装置を通行不可として計算
- カラー壁は、同色のスイッチと色つき木箱が初期配置に揃っている場合のみ通行可能として計算する
- マグマは、足場用のノーマル木箱が1つもない場合のみ通行不可として計算する
- ただしコピー&ペーストによる箱の生成・切り取りによる除去は考慮しないため、**警告扱い**とする
- 将来、メカニクスを考慮した厳密判定を追加する場合はエラーへ昇格できるよう、判定関数を分離する

### 7.5 ステージ間の整合性

- `id` の一意性
- `number` の一意性
- `number` の欠番・重複
- 全ステージ数が0でないこと
- 将来: ボス発生ステージ番号との整合性

## 8. ゲーム側の取り込み設計

### 8.1 ビルドツールの導入

現状はビルドなしのため、以下を導入する。

- ゲーム用 `package.json` と Vite
- 開発: `npm run dev`
- 本番: `npm run build` → `dist/`
- ビルド前フックで `validate:stages` を実行
- 出力は静的ファイルのみ。実行時サーバー不要

Viteは**ビルドツール**であり、ゲームの実行時依存は増やさない。Canvas APIのままとする。

### 8.2 自動検出

`src/data/stages.js` をローダーに変更し、Viteのglob importで `src/data/stages/*.json` を**ビルド時に列挙**する。

- 新しいJSONをフォルダに置くだけで検出される。`stages.js` への追記は不要
- JSONはJSバンドルに静的に含まれるため、実行時fetchは行わない
- 読み込み後、`schemaVersion` を確認し、正規化・検証する
- `number` 昇順、同値なら `id` 昇順でソートして `STAGES` として公開する
- `StageManager` のインターフェースは変更しない

### 8.3 既存ステージの移行

1. `src/data/stages.js` の2ステージを、意味を変えずにJSONへ変換する
2. ファイル名は `id` に合わせる（例: `crate-intro.json`、`copy-gate-maze.json`）
3. 既存の `number` を維持する
4. 移行後に全ステージを起動し、壁・アイテム・木箱・ゲート・ゴール条件が一致することを確認する
5. 問題があれば移行前の定義に戻せるよう、移行コミットを分ける

### 8.4 エラー時の挙動

- **ビルド時**: 不正ステージが1つでもあればビルド失敗。ファイル名とエラーIDをログに出す
- **開発時**: 同じく失敗させ、どのファイルが原因か即座に分かるようにする
- **本番実行時**: 不正ステージは存在しない前提。念のためローダーでも検証し、失敗時はコンソールに明示する
- 不正ステージを黙ってスキップする挙動は採用しない（ステージ欠番に気づけないため）

### 8.5 ステージ追加の開発者体験

```text
1. editor でステージを作る
2. {id}.json をダウンロード
3. src/data/stages/ に置く
4. git add / commit / push
5. Cloudflare が自動ビルド
6. 番号順にステージが追加される
```

コード変更・`stages.js` 編集・Cloudflare設定変更は一切不要。

## 9. Cloudflareデプロイ設計

### 9.1 ゲームサイト（Cloudflare Pages）

| 項目 | 値 |
|---|---|
| リポジトリ | 本リポジトリ |
| プロダクションブランチ | `main` |
| Root directory | `/` |
| Build command | `npm ci && npm run build` |
| Build output directory | `dist` |
| Node.js version | 20 または 22（`.nvmrc` / `NODE_VERSION` で固定） |
| Preview deployments | 有効（PRごとにプレビューURL） |

`npm run build` の内部順序:

1. `validate:stages`（全JSON検証）
2. Viteビルド（JSONをglobで取り込み）
3. 出力 `dist/`

検証に失敗するとビルドが失敗し、本番へデプロイされない。

### 9.2 エディタサイト（Cloudflare Pages）

| 項目 | 値 |
|---|---|
| リポジトリ | 本リポジトリ（ゲームと同じ） |
| プロダクションブランチ | `main` |
| Root directory | `editor` |
| Build command | `npm ci && npm run build` |
| Build output directory | `dist` |
| 独自ドメイン例 | `editor.example.com` |

### 9.3 キャッシュと配信

- Viteのハッシュ付きアセット: `Cache-Control: public, max-age=31536000, immutable`
- `index.html`: キャッシュ無効（`no-cache`）とし、デプロイ直後に最新を取得
- JSONはバンドルに含まれるため、追加のキャッシュ設定は不要
- SPAルーティングは使わないため、`_redirects` は原則不要

### 9.4 環境変数

| 変数 | 用途 | 設定先 |
|---|---|---|
| `NODE_VERSION` | ビルド環境固定 | 両プロジェクト |
| `GITHUB_TOKEN` | Phase Bの公開APIのみ | エディタプロジェクトのシークレット |
| `ALLOWED_ORIGIN` | Phase BのCORS制御 | エディタプロジェクト |

MVP（Phase A）ではシークレットは不要。

### 9.5 代替案と不採用理由

| 案 | 判定 | 理由 |
|---|---|---|
| 実行時fetch + 手書きmanifest | 不採用 | manifest更新忘れが起きる。ビルド時globで解決 |
| Cloudflare R2 / KVにJSONを置く | 不採用 | リポジトリを正とする要件と合わず、バックアップ・レビューが弱い |
| ゲームとエディタを同一サイトに同居 | 不採用 | エディタを公開したくない場合に分離できない。バンドルも肥大化 |
| エディタを別リポジトリ | 保留 | スキーマ共有が面倒。まずは同一リポジトリ内 `editor/` を推奨 |

## 10. 自動公開（Phase B）設計

### 10.1 目的

エディタの「公開」操作だけで、GitHub上の正しい場所へJSONを追加し、Cloudflareのビルドを走らせる。

### 10.2 構成

- エディタプロジェクト内の **Cloudflare Pages Functions** に `/api/*` を実装
- エディタとAPIが同一オリジンになるため、CORSを最小化できる
- 管理画面は **Cloudflare Access** で保護（チームのGoogle/GitHubアカウントのみ許可）
- Functionsはサーバー側でのみ保持する**fine-grained PAT**でGitHub APIを呼ぶ
  - 対象リポジトリ限定
  - `Contents: Read and write`、`Pull requests: Read and write` のみ
  - ブラウザには一切渡さない
- 本番運用に移行する場合はGitHub App（インストールトークン）へ移行し、PATを廃止する

### 10.3 公開フロー（PR方式・推奨）

```text
エディタ
  │ 1. 検証OKのJSON + 公開モードを送信
  ▼
Pages Function /api/publish
  │ 2. 認証（Cloudflare Access）
  │ 3. スキーマ検証・id/number重複確認
  │ 4. 既存ファイルのSHA確認（上書き競合対策）
  │ 5. ブランチ stage/{id}-{timestamp} を作成
  │ 6. src/data/stages/{id}.json をコミット
  │ 7. main宛のPRを作成
  ▼
GitHub
  │ 8. CI（validate-stages）とCloudflare Previewビルド
  ▼
レビュアー
  │ 9. プレビューで確認してマージ
  ▼
Cloudflare本番ビルド → ゲームに反映
```

### 10.4 API仕様（案）

| メソッド | パス | 用途 |
|---|---|---|
| `GET` | `/api/stages` | 既存ステージ一覧（id, number, name, 更新日時） |
| `GET` | `/api/stages/{id}` | 既存JSON取得（編集用） |
| `POST` | `/api/publish` | 新規追加・更新。PR作成またはmain直コミット |
| `POST` | `/api/validate` | サーバー側検証のみ（任意） |

`POST /api/publish` の入力（案）:

```json
{
  "stage": { "...": "ステージJSON本体" },
  "mode": "pull_request",
  "baseSha": "既存ファイル更新時のSHA"
}
```

レスポンス:

```json
{
  "ok": true,
  "pullRequestUrl": "https://github.com/.../pull/123",
  "previewUrl": "https://...pages.dev"
}
```

### 10.5 競合・更新ルール

- `id` は新規作成後変更不可
- 既存 `id` の更新時は、GitHub Contents APIの `sha` を必須とし、古いSHAなら409を返す
- `number` の重複は公開前にサーバー側で再確認
- 同一ステージの同時編集は「後勝ち」にせず、競合エラーとして再読み込みを促す
- 削除はPhase Bの対象外（必要ならPRで手動削除）

### 10.6 直コミットモード

- チーム内の信頼できる操作者のみ、`mode: "direct"` を許可
- それでもCI検証は必須
- ブランチ保護により、PR方式ではレビュー1名を必須とする

### 10.7 セキュリティ要件

- `id` はホワイトリスト形式のみ許可し、パス結合に使わない（パストラバーサル防止）
- 受信JSONは既知フィールドのみを明示的に取り出して再構築する（プロトタイプ汚染防止）
- ボディサイズ上限64KB、レート制限（例: 10回/分/ユーザー）
- エラーメッセージにトークンや内部URLを含めない
- 監査用に「誰が・いつ・どのidを公開したか」をCloudflare Logsへ記録

## 13. 受け入れ基準

1. `src/data/stages/` に有効なJSONを1つ追加してmainへpushすると、ゲームのビルドが成功し、`number` の順にステージが追加される
2. 追加のために `stages.js` やその他のコードを編集する必要がない
3. エディタで既存JSONをインポートし、編集してエクスポートできる。再インポートしても意味的な差分がない
4. エディタ上で開始位置・ゴール・壁・アイテム・木箱・ゲート・goalBlockが視覚的に区別できる
5. 不正な配置（重複、範囲外、必須欠落）はエディタでエラー表示され、エクスポートできない
6. 不正なJSONが混入した場合、CIとCloudflareビルドが失敗し本番にデプロイされない
7. エディタはゲームとは別URLで動作し、ゲームのバンドルにエディタコードが含まれない
8. 既存2ステージの挙動（壁・アイテム・木箱・ゲート・ゴール条件）が移行前と一致する
9. Phase Bを有効化した場合、エディタの公開操作からPRが作成され、プレビューURLが返る
10. Cloudflareのビルド設定が文書化され、第三者が同じ設定を再現できる

| 8 | 到達可能性をエラーにするか | 警告 / エラー | 現状は警告。検証精度向上後に再検討 |

## 15. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| Vite導入で既存の「index.htmlを開くだけ」ができなくなる | 開発手順の変更 | READMEに `npm run dev` を明記。ビルド成果物は静的のまま |
| エディタとゲームで仕様がずれる | 不正ステージ・表示崩れ | `packages/stage-schema` を唯一の正とする |
| 非エンジニアがGit操作でつまずく | 制作が進まない | Phase AはGitHub Web UI手順を整備。Phase Bでワンクリック化 |
| 検証が厳しすぎて制作意欲を削ぐ | ステージが増えない | 到達可能性などは警告に留める。エラーは構造的な不正のみ |
| ID・番号の重複 | ビルド失敗・上書き | エディタで事前確認、CIで最終確認、更新時はSHAで競合検出 |
| 公開APIのトークン漏洩 | リポジトリ改ざん | サーバー側のみ保持、最小権限PAT、Cloudflare Access、監査ログ |
| ステージJSONの肥大化 | バンドル増 | 1ファイル64KB上限、画像は使わない |
| 既存Undoがアイテム取得を戻さない | 制作時の違和感 | 本設計とは別課題としてゲーム側で改善を検討 |

## 16. まとめ

- **ステージの正は `src/data/stages/*.json`** とし、Viteのビルド時globで自動検出する
- **エディタは `editor/` の独立サイト**としてCloudflare Pagesにデプロイする
- 壁はタイル塗りで編集し、出力時に決定的な矩形へ変換する
- スキーマと検証は共通パッケージに集約し、エディタ・CI・Cloudflareビルドで同じルールを使う
- MVPは「JSONダウンロード → リポジトリへ追加 → 自動ビルド」で完成させ、余力があればPages Functionsによるワンクリック公開へ拡張する
